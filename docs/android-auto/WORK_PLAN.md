# WikiReader Android Auto — техническое задание и автономный план для ChatGPT Work

**Дата подготовки:** 18.10.2026  
**Репозиторий:** `mnevrov/wikimapia-reader` — https://github.com/mnevrov/wikimapia-reader  
**Базовая ветка:** `main`  
**Зафиксированная исходная ревизия на момент подготовки:** `570b69ebe768f82442aa876a051e36dde1d6916f` (`0.7.3`); при запуске сначала проверить текущий HEAD и изменения с этой ревизии.  
**Цель:** полностью реализовать поддержку Android Auto (projected Android Auto) для существующего приложения WikiReader, без отдельного предварительного PoC и без нарушения текущей мобильной версии.  
**Область:** полноценный автомобильный POI-клиент, не turn-by-turn-навигатор. Android Automotive OS не является обязательной целью текущей работы.

## 0. Инструкция Work: автономность и рамки

1. Получи доступ к репозиторию через GitHub, изучи актуальный `main`, историю последних изменений, README, Android-модуль, Capacitor-плагины, React-приложение, API, кэш, тесты и CI. Не принимай этот документ за доказательство состояния после указанной ревизии: актуальный GitHub — источник истины.
2. **Не останавливайся после анализа, описания архитектуры, списка задач или первого рабочего экрана.** Самостоятельно проектируй, реализуй, тестируй, исправляй ошибки, актуализируй документацию и доводи **весь перечисленный ниже функциональный объём** до состояния, готового к пользовательским испытаниям.
3. **Не проводи самостоятельный этап проверки гипотез / Go-No-Go PoC.** По ходу полноценной разработки выполняй необходимые тесты, устраняй обнаруженные ограничения, используй предусмотренные fallback-пути.
4. Создай отдельную рабочую ветку, например `feat/android-auto-full`. Пушь законченные этапы в эту ветку, можешь создавать PR. **Не сливай PR в `main`, не удаляй рабочие пользовательские данные, не переподписывай и не перезаписывай существующую рабочую сборку.** Сохранность текущего приложения важнее быстроты интеграции.
5. Используй минимально достаточную архитектуру и зависимости. Android-разработку веди в совместимом с текущим проектом стиле (Java/Gradle); Kotlin допустим только при обоснованной пользе и без ненужного смешения технологий.
6. Выполняй задачи последовательно, но автономно. Документируй решение при каждом значимом этапе и оставляй изменения в понятных коммитах. Не проси пользователя подтверждать каждую задачу. При реальном внешнем блокере — зафиксируй конкретную причину и заверши всё, что не зависит от него.
7. Не выдавай сборку APK, которая только открывает демонстрационный экран, за готовый Android Auto. Не утверждай, что тесты на реальной машине, лицензирование тайлов или одобрение Google Play выполнены, если этого не произошло.

## 1. Неприкосновенность мобильного приложения

Обязательные инварианты:

- Существующее приложение на телефоне должно сохранять интерфейс и поведение версии 0.7.3, включая исправления свайпов/анимаций, геолокацию, поиск, комментарии, фотографии, настройки, API-ключ, избранное, сохранённые контуры, ограничения загрузки и оформление.
- Рабочая установленная сборка WikiReader Next имеет **`applicationId=org.example.wikimapreader.next` в debug-конфигурации** (по состоянию 0.7.3). Нельзя случайно заменить её экспериментальной сборкой, изменив идентификатор/подпись/существующие данные.
- Подготовь **отдельные Android build variants/flavors** для обычной мобильной сборки и сборки с Android Auto. Например, `mobile` и `autoDev`; точное именование и сочетание с `debug`/`release` выбери после проверки Gradle/Capacitor. Сохрани прежний package/applicationId для существующей мобильной debug-сборки; тестовому автомобильному варианту присвой отдельный уникальный applicationId, например `org.example.wikimapreader.auto.dev` (проверь итоговый merged manifest, учти suffix от buildType).
- Телефонный интерфейс остаётся обычным React/Leaflet/Capacitor-приложением. Android Auto добавляется в собственном native car-компоненте. Не заменяй мобильную карту кар-рендерером.
- Привяжи декларацию CarAppService и связанные ресурсы только к соответствующим вариантам/настройкам, чтобы обычная мобильная сборка не зависела от недоступных автомобильных возможностей. При финальном выпуске с Android Auto можно будет объединить функциональность в одном приложении, **но не ценой перезаписи текущей рабочей установки во время разработки**.
- Настройки, API-ключ и кэш dev-пакета должны физически храниться отдельно (sandbox Android). Тестирование не должно требовать сброса основной установки.
- Не заменяй стабильный keystore временным; не сохраняй ключи/пароли в репозитории; не делай небезопасную миграцию.
- Зафиксируй baseline тестов и сборки до рефакторинга. После каждого этапа прогоняй регрессию телефонов и обе Android-сборки.

## 2. Поддерживаемая платформа и официальные интерфейсы

- Цель — **Android Auto (проекция телефона на автомобильный дисплей)**. Не путай с Android Automotive OS.
- Категория — POI (`androidx.car.app.category.POI`), а не NAVIGATION: приложение показывает места/объекты, не осуществляет turn-by-turn-навигацию.
- Базовая библиотека: стабильная `androidx.car.app:app:1.7.0` плюс поддержка projected Auto `app-projected` и тесты `app-testing`; перед фиксацией зависимостей перепроверь официальную документацию и актуальные security-fix рекомендации. На 18.10.2026 1.8.0-rc01 не является stable, но содержит security fix: оцени это перед выбором версии; если применимо, обоснуй выбранную версию.
- Основной шаблон — `MapWithContentTemplate` с самостоятельно отрисовываемой картой через автомобильную `Surface` и `SurfaceCallback`; требуется уровень Car App API 7.
- Для хостов, не поддерживающих API 7, — корректный fallback `PlaceListMapTemplate` с маркерами и списком, а не краш, пустой экран или фиктивный шаблон. Не обещай отображение полигонов в fallback.
- Зарегистрируй `CarAppService`, car metadata, permissions (в частности `androidx.car.app.MAP_TEMPLATES`) строго по актуальным рекомендациям; `androidx.car.app.NAVIGATION_TEMPLATES` не запрашивать ради POI.
- Поддержи жизненный цикл подключения/отключения, повторное создание session/screen, смену размеров и ориентации, смену освещения/темы, Surface create/change/destroy; корректное прекращение запросов и освобождение ресурсов.
- Не пытайся напрямую перенести WebView/Leaflet в Car App Library, не применяй механизмы обхода автомобильного UI или driver-distraction restrictions.

## 3. Полный функционал автомобильного клиента

### 3.1 Карта

- Показывать картографическую подложку (допустим OpenStreetMap raster tiles либо лицензированный совместимый провайдер), атрибуцию источника, текущее положение и полигоны Wikimapia; подложка не должна скрывать полигоны.
- Стандартные контуры без заливки, выбранный контур визуально выделять; корректная проекция, масштабирование, позиционирование при любом aspect ratio, изменение viewport, обрезка и упрощение геометрии с сохранением достаточной точности.
- Использовать native Surface renderer, который умеет отображать фрагменты карты и полигоны и перерабатывает кадр при изменении состояния без лишней сетевой загрузки; не рендерить на UI thread тяжёлую геометрию/tiles.
- Управление зумом, смещением, восстановление режима слежения за автомобилем, корректная обработка `SurfaceCallback` (`onScale`, `onScroll`, `onClick` и поддерживаемые события), map action strip и доступных действий хоста. Соблюдать car-host ограничения на количество и типы кнопок.
- Начальная позиция: актуальная геолокация, при отсутствии разрешения — последний корректный viewport, затем безопасный дефолт с объяснением. Отключение/слабый GPS не должны приводить к аварии.
- Следование за текущей позицией при движении, разумная частота обновления, ручное перемещение временно отключает follow-mode; одна кнопка возвращает к автомобилю.
- Выбор объекта касанием внутри полигона; если полигоны пересекаются, выбор из списка релевантных объектов, предпочтительно меньших/более конкретных, с сортировкой стабильной и предсказуемой. Отмена выбора безопасна.
- Загрузка и отображение нескольких соседних областей без дыр/мигания там, где имеется кэш и разрешённые данные; не подменять неполное покрытие полной загрузкой.
- Работа на разных разрешениях, плотностях и форматах автомобильных экранов; контрастные подписи и цветовые режимы, минимум визуального шума.

### 3.2 Объекты и карточки

- Для выбранного объекта показывать краткую адаптированную карточку: название, тип/дистанция при наличии подтверждённых данных, лаконичное описание (в рамках car-template), действия «в избранное», «открыть на телефоне» и «построить маршрут», когда данные/хост это допускают.
- По умолчанию не открывать длинные описания, галерею и комментарии на автомобильном экране во время движения: оставить их в полнофункциональном мобильном UI. Не пытаться обходить запреты на UX при вождении.
- Открытие в телефоне сохраняет ID выбранного объекта; при запуске Android-приложения пользователь попадает в нужную карточку. Учесть lifecycle и отсутствие запущенного WebView.
- «Маршрут» передаёт географическую точку установленному совместимому навигационному приложению через официально разрешённый Android Auto intent/action; не создавать фиктивную turn-by-turn-функцию, проверить, что действие действительно разрешено хостом. Для полигонов определить корректную целевую координату (например, вычисленная репрезентативная точка, принадлежащая полигону; проверить невыпуклые формы).

### 3.3 Поиск и избранное

- Отображение объектов поблизости с автомобильным шаблоном, заголовками, контекстом расстояния при наличии геоданных, сортировкой и предельным числом элементов без ухудшения производительности.
- Поиск объектов по названию, Wikimapia ID/ссылке при технической и UX-совместимости; ввод только через car-host шаблоны и разрешённые сценарии. Ошибки/квота/отсутствие сети — понятные состояния, не циклические ретраи.
- Избранное доступно в автомобиле и на телефоне, без потери записей при переходе между интерфейсами. Обеспечь двустороннюю синхронизацию в рамках единого установленного APK; в изолированном `autoDev` данные отдельные, автоматического доступа к базе мобильного пакета быть не должно.
- Последний viewport/выбранный объект можно восстановить, без раскрытия личной информации и без лишних запросов.

### 3.4 Загрузка, сеть, кэш и offline

- Использовать только документированный API Wikimapia (`box`, `search`, `place.getbyid` и согласованные методы), HTTPS, личный API-ключ; не применять Nakarte proxy, scraping, недокументированные itiles или обход лимитов.
- Сохранить действующие семантические ограничения приложения: минимум **6 секунд между запросами Wikimapia**, bbox <= 0.035° по долготе и широте, корректные page/count, проверка ошибок даже в HTTP 200, прерывание устаревших запросов, контролируемые повторы.
- При движении адаптировать изменение viewport и загрузку к доступной частоте API: coalescing, debouncing, приоритет видимой области, кэш и дедупликация, постепенная догрузка с отображением неполного покрытия. Не обещать загрузку каждого объекта на высокой скорости, когда не позволяет API.
- Повторно использовать те же правила нормализации Wikimapia и геометрии, что и в JS. Для Android native слоя допустима реализация JSON contract с общими fixtures и parity-tests; не обязательно дублировать весь JavaScript runtime внутри автомобиля.
- Реализовать native cache контуров/результатов с ограничением размера, TTL, pinning только для контуров, флагами полноты и безопасным обновлением. Текущий `IndexedDB` web-кэш недоступен CarAppService напрямую — нельзя выдавать его за автоматически общий.
- Для финального объединённого приложения продумать безопасный обмен уже накопленными веб-данными и native-данными (однократная миграция и синхронизация в последующих запусках) без потери старых избранных объектов/кэша; обратную совместимость и атомарность покрыть тестами.
- При отсутствии интернета показывать ранее сохранённые контуры/избранное и различимый статус устаревших данных. Полные описания/фото/комментарии offline **не заявлять**, если данные не сохраняются.
- Карта OSM: соблюдать https://operations.osmfoundation.org/policies/tiles/ — идентификация User-Agent, явная attribution, HTTP cache headers, отсутствие массового фонового prefetch/offline download. Если нужен **полноценный offline basemap**, заменить источник на провайдера/локальные данные с явно подходящей лицензией; не делать предзагрузку `tile.openstreetmap.org`.

## 4. Архитектура и взаимодействие с мобильным кодом

Предпочтительная структура (согласовать с реальным Gradle-проектом, не плодить лишние слои):

```text
android/app/src/
  main/java/.../
    MainActivity.java                   # старое мобильное приложение
    .../credentials/...                # общий защищённый доступ к API-ключу
    .../shared/...                     # модель Place, bbox, storage contracts
  mobile/...                           # обычная конфигурация, без AA-регрессий
  autoDev/...                          # отдельный dev applicationId
  .../car/                             # CarAppService, Session, Screens,
                                      # Surface Renderer, POI repository,
                                      # Location, Favorites, Cache, Navigation Handoff
src/
  ...                                  # React/Capacitor не переписывать
  ...                                  # только минимальная интеграция bridge/sync
```

Уточнение: `src/main/java` и source sets могут быть организованы иначе; **безопасность package naming и вариантов сборки важнее точного расположения файлов**. Не вводить два Android app-модуля, если flavors решают задачу проще.

- Сохранить Android Keystore AES-GCM и ciphertext-only схему действующего `CredentialsVaultPlugin`. Для чтения ключа из CarAppService выделить безопасный внутренний `CredentialRepository` с общим контрактом; хранить только в app-private хранилище, не логировать и не передавать в URL логов/события/краш-отчёты. Существующие зашифрованные записи должны быть читаемы после рефакторинга (не менять alias/AAD без миграции).
- Сеть, модель, кэш и навигация — за интерфейсами, тестируемыми в JVM без реального автомобиля. Потоки запросов должны быть сериализованы/ограничены и отменяемы, таймауты заданы.
- Для обмена с существующими избранным и IndexedDB построить versioned bridge/repository с миграцией, а не считать `localStorage` и `IndexedDB` доступными из нативного сервиса. Миграция idempotent, без дубликатов, с возможностью восстановления из старого формата и тестами сценариев первого запуска сразу в автомобиле.
- Не менять существующий `MainActivity` сильнее, чем требуется для bridge/deep-link, и не ломать текущую аппаратную/системную навигацию телефона.
- Никаких дополнительных обязательных серверов, токенов, прокси, платных API. При необходимости внешнего tile provider объяснить почему и не подменять решение несовместимым сервисом.

## 5. Этапы автономной реализации (все обязательны)

### Этап 1 — Baseline и изоляция
- Прочитать дерево репозитория/CI/последние коммиты.
- Выполнить и зафиксировать доступные mobile tests/build/lint, определить истинный Gradle applicationId и подпись для каждого варианта.
- Добавить `mobile` / `autoDev` варианты, ensure separate data sandbox, выпуск двух APK, обновить CI artifacts с однозначными именами.
- Убедиться, что новый native car-код не попадает в обычную сборку непредвиденным образом.

### Этап 2 — Автомобильная платформа
- Добавить совместимые AndroidX зависимости, service/manifest/XML, POI category, map permission, app-testing.
- Создать полноценные `CarAppService`, Session, Screen lifecycle, host capability detection, минимум ошибок/состояний.
- Реализовать fallback на старый host (`PlaceListMapTemplate`), полноценный современный экран (`MapWithContentTemplate`) без выделения отдельного PoC.

### Этап 3 — Общие данные и безопасное хранилище
- Реализовать Android-native Wikimapia HTTP client, валидаторы/mapper, global 6 s throttle, quota/backoff/cancellation.
- Выделить credential repository, безопасный native cache, favorites bridge, versioned migration, fixtures/parity tests.
- Добавить восстановление из процесса, переход с телефона на car и наоборот, ошибки доступа к ключу.

### Этап 4 — Полная карта, объекты и управление
- Surface rendering тайлов/полигонов, взаимодействия zoom/pan/click, следование GPS, selection/overlapping polygons, multiple bbox/cache, responsive layouts/night mode.
- Поиск рядом, текстовый поиск/ID, POI list, object details summary, favorites, navigation handoff and open-on-phone.
- Состояния offline, empty, no API key, quota exceeded, no location, slow network, low-memory; не блокировать карту «загрузкой» поверх сохранённых данных.

### Этап 5 — UX/надёжность/безопасность
- Довести эргономику Car App Library templates: не перегружать кнопками, быстрый возврат к карте, понятные состояния, адекватная доступность, локализация на русском, шрифты/контраст.
- Система обновлений не должна бесконечно делать API вызовы при движении, свёрнутом приложении, смене orientation, нажатиях или падении сети.
- Документировать отсутствие гарантий всех объектов Wikimapia и ограничения driving-safe UI.

### Этап 6 — Проверка всей функциональности и финализация
- Выполнить мобильные регрессионные тесты + Android Car app testing и Gradle lint/test/assemble для **обоих** вариантов.
- При доступности DHU — сценарные испытания Android Auto на Linux, screenshots/лог ошибок/матрица устройств; при недоступности DHU зафиксировать NOT_RUN и не выдавать unit tests за UI-проверку.
- В CI собирать отдельный `autoDev` APK, артефакты и checksums; существующий APK остается доступным и не замещается.
- Подготовить понятную русскую документацию по установке/запуску и troubleshooting. PR с архитектурой, test evidence, результатами и честными остаточными ограничениями.

## 6. Тесты и контроль качества

### Автоматические обязательные проверки

1. Existing `npm test`, `npm run test:probe`, `npm run test:browser` с существующими фикстурами.
2. Gradle unit, lint и APK assemble для mobileDebug и autoDevDebug (реальные имена после конфигурации). Тесты гарантируют, что applicationId и merged manifests имеют требуемые отличия, signing не нарушен.
3. Car app-testing: создание сервиса/сессии/экранов, выбор шаблонов и fallback на API<7, навигация между POI экранами, основные действия, восстановление после session recreate.
4. Контрактные тесты API: bbox, пагинация, errors in 200, отсутствие ключа, invalid polygon, quota, cancellation, throttle>=6s, конкурентные запросы, кэш-попадания и пропуски, ограничения размера/давности, ID/search.
5. Тесты синхронизации: migration старых bookmarks, namespace demo/live, изменения с двух интерфейсов, dedup, переход на native storage, reset и recover без потери пользовательских данных.
6. Тесты геометрии: longitude/latitude order, Mercator, antimeridian/bounds, вложенные и пересекающиеся полигоны, tap hit-test и центроид/representative point, zoom, поворот/изменение surface size.
7. Проверка ресурсов: teardown Surface, уход/возврат из Auto, отсутствие утечек и бесконтрольных таймеров, офлайн и слабая сеть, отсутствие ключа в CI/logcat/artifacts.

### При доступности DHU (с фактическими screenshot/evidence)

- Старт Auto с запущенным телефоном / без телефона UI в foreground / после перезапуска процесса.

- Отображение контуров в Москве на реальной подложке с подтверждённым ключом **локально, не хранить ключ в CI**.
- Выбор нескольких объектов в одной точке, карточка, маршрут во внешнем навигационном приложении, открытие карточки в телефоне.

## 7. Критерии приёмки / Definition of Done

**Готово**, когда выполнено **всё** следующее:

- [ ] На телефоне сохранён функционал и UX версии 0.7.3; полный набор текущих тестов зелёный.
- [ ] Исходное установленное приложение `org.example.wikimapreader.next` не повреждено и не требует удаления/переустановки для тестирования авто-режима.
- [ ] Android Auto dev устанавливается отдельно, имеет собственный package/data/keystore context.
- [ ] На поддерживаемом хосте Auto есть рабочая карта с базовым слоем, полигонами Wikimapia, GPS/follow, pan/zoom и выбором объектов; для раннего host корректный POI fallback.
- [ ] Реально работают список ближайших объектов, поиск, избранное, краткая карточка, передача маршрута, открытие на телефоне, обработка пересекающихся объектов.
- [ ] Работают безопасные credentials, контролируемый Wikimapia API, native cache, понятные offline/errors; нет запроса каждые секунды в нарушение API политики.
- [ ] При интегрированном варианте избранное сохраняется при обмене между mobile и car; тестируются миграция и отсутствие потери данных. Раздельная dev-сборка закономерно хранит независимые данные.
- [ ] Выполнены Android unit/lint/build обеих сборок, Car app tests, JS/Playwright regressions; CI сохраняет оба APK/checksums, реальные результаты зафиксированы.
- [ ] Документация, архитектурная схема, инструкции CI/DHU/установки, matrix tests/known limitations обновлены.
- [ ] Нет изменений в `main`, пока пользователь явно не разрешит слияние; итоговый PR готов к ревью.

**Если среда Work не имеет Android SDK/DHU или не может запустить реальные APK:** всё равно завершить код, CI и документацию, выполнить доступные проверки, оставить проверяемые артефакты; честно пометить блокированные тесты `NOT_RUN`, не объявлять неподтверждённые критерии завершёнными. Не останавливаться после первого препятствия, если остальная работа выполнима.

**Публикация в Google Play не является условием готовности к тестированию.** Android Auto POI-категория и содержание WikiReader должны отдельно пройти требования Google по безопасности и полезности для водителя (в т. ч. PF-1); одобрение нельзя гарантировать. Отдельно объяснить поддерживаемые каналы установки на физический автомобиль.
